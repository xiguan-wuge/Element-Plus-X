# 富文本实现原理

> 本文回答三个问题：contenteditable 的本质是什么？现代编辑器与「第一代编辑器」的差别在哪？在 Vue 中内容里嵌入组件有哪些方案？

## 1. contenteditable 的本质

给元素设置 `contenteditable="true"` 后，浏览器将该区域变为可编辑区域，用户输入的一切都会**直接变成真实 DOM**。第一代编辑器（UEditor、早期 wangEditor 等）配合 `document.execCommand('bold')` 等命令直接操作 DOM，序列化时取 `innerHTML` —— 所以产物天然是 HTML 字符串。

这条路存在固有问题：

| 问题       | 说明                                                                   |
| ---------- | ---------------------------------------------------------------------- |
| 产物不可控 | 不同浏览器生成的标签不一致（`<b>` vs `<strong>`、冗余 style 标签）     |
| DOM 即真相 | 程序难以理解文档结构（哪个是标题、哪个是卡片？）                       |
| 与框架冲突 | 直接 DOM 操作打乱浏览器原生撤销栈，也和 Vue/React 的声明式渲染互相覆盖 |
| API 废弃   | `document.execCommand` 已被标准废弃                                    |

## 2. 现代编辑器的核心：Model-View 分离

第二代编辑器（Quill、Slate、ProseMirror/Tiptap、Draft.js）的关键转变：**contenteditable 只作为「输入层」**，文档真相是一个结构化数据模型：

| 编辑器               | 数据模型                                             |
| -------------------- | ---------------------------------------------------- |
| Quill                | Delta（JSON ops：`{ insert, attributes }`）          |
| ProseMirror / Tiptap | 受 Schema 约束的 Node 树，每次修改是一次 Transaction |
| Slate                | JSON 文档树，完全由框架控制渲染                      |

工作流程：

```
用户键入 → beforeinput/IME/selection 事件 → 转换为对数据模型的修改
        → 框架声明式重新渲染 → contenteditable 区域被同步
```

HTML 只是数据模型的一种导出格式。协同编辑（Yjs + ProseMirror）也建立在这个模型之上。

## 3. 关键问题：v-html 里 Vue 组件为什么不生效？

```html
<div v-html="html"></div>
<!-- html 里写 <el-button> 不会工作 -->
```

Vue 组件的编译发生在**构建时**（SFC 编译）或 **app 挂载时**，而 `v-html` 本质是 `innerHTML`，插入的 DOM 完全不经过 Vue 编译器——没有组件实例、没有响应式、`@click` 不会绑定、props 不生效，标签只是 unknown element。

## 4. 在内容中嵌入 Vue 组件的方案

### 场景 A：只展示（渲染态）

| 方案                     | 思路                                                                           | 适用                        |
| ------------------------ | ------------------------------------------------------------------------------ | --------------------------- |
| AST → VNode 转换（推荐） | 解析为 AST，遍历时把特定节点替换为组件 VNode（如 `markdown-it → hast → h()`）  | Markdown / 结构化内容       |
| Web Components           | `defineCustomElement` 编译为原生 Custom Element，HTML 字符串原生可识别         | 跨技术栈、CMS 下发          |
| 占位符 + 手动挂载        | HTML 中放 `<div data-widget="chart">`，渲染后 `createApp().mount(el)` 逐个挂载 | 简单场景，需自管生命周期    |
| 运行时模板编译           | `Vue.compile(htmlString)`（需 runtime-compiler 构建）                          | 不推荐：XSS 风险 + 编译开销 |

> 所有接收外部 HTML 的方案都应先用 DOMPurify 等做 sanitize。

本库 `XMarkdown` 采用的即是 **AST → VNode + 组件映射** 模式：`customComponents` 通过具名插槽传给渲染器，在 AST 对应节点处渲染真正的 Vue 组件（CodeBlock、Mermaid、RunCode 等）。

### 场景 B：编辑态嵌入组件（@提及、词槽、卡片、图表）

这类需求叫**原子块（atom / embed block）**，核心思路：组件在数据模型里是一个**结构化节点**，而不是 HTML：

```jsonc
// ProseMirror/Slate 风格的文档模型
{ "type": "paragraph", "content": [{ "type": "text", "text": "看这个图表：" }] }
{ "type": "chart", "attrs": { "chartId": 123 } }  // 自定义节点
```

各编辑器的实现钩子：

- **Tiptap (ProseMirror)**：自定义 Node + `VueNodeViewRenderer(MyVueComponent)`；节点 DOM 标记 `contenteditable="false"`，光标整体跳过它
- **Slate**：渲染层判断 `element.type` 直接渲染组件，包一层 `contenteditable=false`
- **Quill**：注册自定义 Embed Blot，在 blot 的 DOM 节点里挂载组件
- **Notion 式 block 编辑器**：每个 block 独立组件、甚至独立 contenteditable，块之间不在同一可编辑树

组件对编辑器来说只是文档里一个不可拆分的节点；序列化时输出占位标签或结构化数据，回显时还原。

## 5. 小结

- contenteditable 产出 HTML 只是表象；现代编辑器的核心是**结构化文档模型**。
- Vue 组件无法「活」在 HTML 字符串里，但可以活在 **AST 节点映射**（展示态）和**自定义节点 / NodeView**（编辑态）中。
- 词槽、@提及属于「内联原子块」这一轻量子集，可以不引入完整编辑器框架，用 contenteditable + 原子块 + 直接 DOM 操作实现——这正是 ant-design-x Sender 的做法（见下一章）。
